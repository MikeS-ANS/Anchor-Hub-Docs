# v3.5.3 — Strety widget: access token going invalid mid-session

Follow-up patch to the v3.5.1/v3.5.2 Strety widget fixes.

## Fix

v3.5.1 and v3.5.2 fixed problems with the shared *refresh* token going dead. This patch fixes a related but distinct problem with the *access* token — the short-lived token used for the actual data calls.

Strety can invalidate a cached access token earlier than our own expiry bookkeeping expects — for example, when another user's app (or a scheduled task) rotates the shared refresh token in the meantime. When that happened, the widget had no way to notice: it kept using the now-dead access token, got a raw `401 INVALID_TOKEN` error back from Strety, and showed that as a generic error — even immediately after a successful reconnect.

Now, `stretyGetUrl()` treats a 401 on the actual data call as a signal that the cached access token is stale, regardless of what our own expiry timer says:

- It drops the cached token and forces one real refresh against whatever refresh token Key Vault currently holds.
- It retries the request once with the freshly-refreshed token.
- If it's still invalid after that, it's tagged with the same `needsReconnect` signal used by the v3.5.2 fix, so the widget offers the Connect prompt instead of a raw error.

No user action needed — if you hit a raw "Strety unavailable" or 401-style error mid-session, it should now either recover silently or offer the Connect prompt.

**Still open, not fixed by this patch:** all three of these Strety widget patches (v3.5.1, v3.5.2, v3.5.3) trace back to the same root cause — multiple independent app instances sharing one refresh-token credential in Key Vault with no coordination between them. Whether non-admin users should get Key Vault write access to that secret, or whether refresh should be centralized into an admin-only process instead, is a deliberate architectural call still pending with Mike.

See [Roadmap](../getting-started/roadmap.md) for where this sits alongside the v3.5.0 widget and the v3.5.1/v3.5.2 patches it follows.
