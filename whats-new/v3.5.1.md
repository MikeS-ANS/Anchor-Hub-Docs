# v3.5.1 — Strety widget: refresh-token race + dead-end fix

Quick patch fixing a live bug in the v3.5.0 Strety Rocks & To-Dos homepage widget.

## Fix

The shared Strety refresh token could go dead, and once it did, the widget had no way back to the Connect flow — it just showed "Strety unavailable" forever.

Two things were happening:

- Strety rotates refresh tokens on every use. If two refreshes happened at nearly the same time (e.g. two widget loads racing on startup), both tried to redeem the same token — the second one burned it, since it had already been rotated out by the first.
- A failure to persist the newly-rotated token back to Azure Key Vault was silently swallowed, so a refresh could "succeed" locally while the vault still held a now-invalid token.

Once the token was dead, there was no recovery path: `strety-check-connected` only checked whether *a* token existed, not whether it still worked, so the widget kept reporting connected and never re-offered the "Connect Strety" prompt.

Now:

- Concurrent refresh calls dedupe onto a single in-flight grant call instead of racing.
- A failed write-back to Key Vault is logged instead of swallowed.
- A confirmed-dead token (a 400 response on refresh) is cleared from Key Vault, so the widget self-heals back to the Connect strip within the same page load instead of dead-ending.

No user action needed — if your widget was stuck showing "Strety unavailable," it should now offer the Connect prompt again on next load; just reconnect once.

No other changes in this release. See [Roadmap](../getting-started/roadmap.md) for where this sits alongside the v3.5.0 widget it patches.
