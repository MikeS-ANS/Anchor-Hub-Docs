# v3.4.3 — User Audit Report write-back duplicate-contact safeguard

## Fix

**Write-back could silently create a duplicate Autotask contact when a client's email had drifted.** Matching an M365-only user against Autotask was email-only — if a contact's Autotask email no longer matched their current Microsoft 365 address (a typo, a domain rename, an alias), the person's name was clearly the same but the tool had no way to notice, so confirming their row created a brand-new contact instead of updating the one that already existed.

M365-only rows in the write-back preview are now also checked by **name** against the client's own Autotask contacts (last name plus a first-name prefix or close fuzzy match — deliberately biased toward flagging, since a false positive just costs one extra click):

- A likely match shows an **⚠ warning badge** with the matched contact's name and email.
- Flagged rows require an explicit **"Update existing" vs. "Create new anyway"** choice per row — there's no bulk/auto-resolution for a likely duplicate, and leaving neither option selected excludes the row from that write-back the same as leaving a normal row unchecked.
- Choosing **Update existing** updates the matched Autotask contact's classification and email (moving the old address to the secondary email slot if one wasn't already in use there).
- A **live re-check** against Autotask's current contacts runs immediately before every create — not just against the possibly-stale generated report — so a name match that only shows up in Autotask today is blocked with a **needs-review** status in the write-back progress list instead of silently creating a duplicate.
- The write-back summary and account note now call out matched-and-updated contacts and any needs-review count separately from ordinary creates/updates.

See the [User Audit Report guide](../tool-guides/user-audit-report.md) for how to work through a flagged row.
