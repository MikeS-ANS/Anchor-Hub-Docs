A live spike against a single disposable zero-reimbursement report settled the question the phase was built to answer: **Autotask's `ExpenseReports.status` cannot be written through the API at all.** Both `PATCH /ExpenseReports {id, status:5}` and a full-entity `PUT` came back `HTTP 200` with a success-shaped body — the identical shape a genuine write returns — and left the field unchanged; read back twice to be sure. `isReadOnly: true` on the field's own metadata turned out to be accurate, confirmed against the REST and SOAP docs and against Autotask's own statement that read-only fields are silently ignored rather than rejected. So Phase 6 performs **no Autotask write of any kind.** A payroll admin instead reviews a generated XLSX in an editable preview and presses **Approve & Send**, which emails Puzzle to kick off the actual payroll run. The workbook carries **the same ten columns as the review screen, in the same order**, and lists **only the employees who actually have a change this period** rather than the whole roster — both narrowed from the legacy layout after Mike read a real output (the six columns `phase25` dropped as unused are gone from it entirely, not emitted blank as first built). It is written with `exceljs` rather than SheetJS, whose community edition cannot write cell styles at all, so the file arrives with a bold frozen header, real currency formatting, and column widths that do not need expanding — with one distinction preserved through the library switch and worth keeping: a *not-measured* value writes a genuinely empty cell while a *measured zero* writes `$0.00`, because telling a payroll processor "nothing owed" about somebody who may never have been paid is the failure this whole phase is built around avoiding. Because the Hub can't flip the matching expense reports to Paid itself, Send tells a human exactly which reports need that manual flip, through two independent channels neither of which is a fallback for the other: a separate emailed action list at the moment of the send (never appended to the Puzzle email itself, and addressed to its own internal "Notify" recipient set on the send screen — falling back to whoever pressed Send when that is left blank), and a standing in-app panel — reports, amounts, and how many days each has been waiting — with deliberately no dismiss button. The panel clears only through reconciliation: the daily Functions sync re-reads each candidate's live Autotask status and stamps the Hub's own `paidAt` only on an *observed* status of exactly `5`, never on `4` (Rejected), `6`, or a report absent from the read. **`needs_attention` reports are still never auto-settled** — a real person may never have been reimbursed, and that state is the only signal anyone gets — but Phase 6 finally gives them a way to clear: automatically, when the daily sync sees the report's status move off `3` in Autotask, or explicitly, via a required-reason "Mark as handled" that retires the warning without ever touching `paidAt` or Autotask. Sending a period locks its entries to further edits; a new **Reopen** action (not in the original spec, added because a period stuck `sent` with no way back is exactly the hand-run-SQL trap this tool exists to end) undoes only the send record — it never un-marks a report already flipped in Autotask and never resets how long an outstanding one has been waiting.

  **Phase 7 — proactive Teams reminders** *(2026-08-27, the last phase)*. Phase 6 left two recurring manual steps that fail the same way, silently and cumulatively: a manager ticking their sign-off box, and a human flipping expense reports to Paid in Autotask because the API refuses to. Phase 7 is the push half — four notifications over one reusable transport. A **heads-up two business days before** a period's sign-off deadline; **escalation three times every business day** (deliberately reduced to once a day at weekends, because three DMs on a Sunday about work nobody can do is how a bot gets muted, and a muted bot then fails silently for every other Hub tool meant to reuse it) from the day after the deadline until the manager signs off or the period stops being open; a **Monday digest** of expense reports still awaiting their manual flip, aged from when somebody was *first* told rather than from the last reminder; and a **notice to a manager** whenever a payroll admin signs off or reopens on their behalf. **There is no app-only Graph path to a Teams chat message** — `POST /chats/{id}/messages` lists exactly one Application permission in both v1.0 and beta, `Teamwork.Migrate.All`, which only works against a chat in migration mode — so no amount of admin consent lets an unattended sender use Graph chat, and the transport is an Azure Bot posting through the **Bot Connector** instead. It is built as a generic Hub capability (`functions/src/lib/hubTeamsNotify.js`, holding no payroll concept at all) precisely so Timesheet Review, Meraki license expiry and Client Touch Aging can reuse it; Graph appears once, resolving an email to a directory object id, since Teams will not proactively message by email or UPN. The policy (`functions/src/lib/ppReminders.js`) is pure and testable against any instant, and all scheduling lives in code against `America/Denver` behind an **hourly** Timer — which names no wall-clock hour and is therefore immune to `WEBSITE_TIME_ZONE`, unlike the two UTC-encoded crons beside it in the same file. Every send is claimed in a `pp_notifications` ledger with a `UNIQUE` dedupe key **before** it goes out, so three-a-day escalation cannot double-fire; the one place that guard trades against a missed message it deliberately **inverts Phase 6's rule** and risks the duplicate, because a repeated reminder is a nuisance while a missing one is the exact failure this phase exists to end. Reminders ship **switched off** and are armed by hand from a Review & Send panel that previews exactly what would be sent, to whom, without claiming or sending anything. That panel also carries a standing delivery-health line, loaded with no click: a recipient whose Anchor Hub Teams app isn't installed, who has blocked it, or whose address can't be resolved is shown as receiving nothing, and "could not be checked" is rendered distinctly from "nothing has failed" because the two are different facts. Content rules are stricter than the app's own screens — a DM can be forwarded and read outside the role gate, so **no message carries a dollar amount or an employee name**. Declared scope creep, included because the reminders fire off it: `deadlineDate` had been **four calendar days** before the pay date for six phases, not the four business days its own schema comment and the spec both claimed, which put two of the next four deadlines on a weekend; `buildPeriod` now walks business days, for **new periods only** — recomputing an open period moves its deadline earlier and could tip it into overdue the instant it deployed.

- [ ] **Daily Progress** — Phases 1–2 of 3 built on `feature/daily-progress`, not yet released *(spec: `DAILY_PROGRESS_SPEC.md`)*

  **Phase 4** (2026-08-29) builds out the three tabs Phase 3 rendered as placeholders and closes the very first gap this feature exists to fix. **Tools tab** — a read-only registry of the Hub's tools, synced from the app's own tool list whenever an admin launches it (not at deploy time), showing each tool's category and how it's granted — a role count, **Dedicated gate** for Payroll's own separate permission, or **By individual grant only** for Access Management itself — plus a People count of how many active users these tables *would* grant the tool to, distinct from who can actually open it today. **Title Mapping tab** — create, edit, reorder (▲/▼, first-match-wins precedence, refused with a plain-language `409` and a fresh re-read if the list changed under you), retire and restore pattern-to-role mappings (`*` wildcard, `|` alternatives, case-insensitive, whitespace-collapsed, a catch-all pattern refused); Payroll can't be mapped here either. **None of it does anything yet** — no job titles are stored in the Hub, so every mapping's Matched count reads a dash; these are mappings waiting for Phase 5's auto-assignment. **Audit Log tab** — every write this screen has ever made, filterable server-side by category, break-glass use, a person/summary search, and a date range, with keyset paging and a running total so nothing is silently hidden past a page boundary; readable only by an Access Admin, unlike the Hub's shared activity log. **Per-user override editor** — grant, deny, or clear an individual tool for a person from their expanded row, grouped by category, disabled rather than silently re-run when the selected effect is already in force (protects the provenance on an existing grant); granting or revoking Access Admin itself goes through the same typed-name confirmation either direction, and a person can no longer revoke their own — closing the gap where a mistaken Access Admin grant needed hand-run SQL to undo. Also fixed: the sidebar's `Checking access…` placeholder, shown only while the one-time launch permission check hasn't resolved yet, so a slow check reads as "still checking" rather than an entry that mysteriously appears moments later. **Still unchanged, as of this Phase 4 snapshot: nothing yet read these tables for real access** — `getAllowedToolKeys()` still resolved everyone's actual sidebar from SharePoint and the Entra token at the time, until the Phase 6 cutover below (now shipped, and `getAllowedToolKeys()` itself deleted outright in Phase 6 Task 7).

  **Phase 5** (2026-08-30) ships the feature's actual auto-assignment: `POST /access/users/self` — already called on every launch — now reads the signer's Entra job title **server-side**, using the Function App's own managed identity (Graph `User.Read.All`, application-only; the client never supplies a title, closing the obvious self-assign-by-claiming-a-title hole). On a person's genuinely first sign-in only (`created` or a first-time `objectId` bind — deliberately *not* "currently holds no role," so a role an admin removed on purpose is never silently reinstated), the title is matched top-down against active Title Mapping rows and a match is auto-assigned (tagged `auto`, `matchedPattern` recorded); a `manual` row is never touched, by construction — the write is an `INSERT ... WHERE NOT EXISTS` with no `UPDATE` branch to overwrite anything. No match, and the person lands on Pending exactly as before. **Every Access Admin now gets a Teams DM the moment someone lands on Pending** — reusing Phase 7 (Payroll Processing)'s notification transport, deliberately generic since day one — worded so it names no one: no name, email, or title, since a Teams message is forwardable and sits outside every permission gate the Hub has; it's a pointer to the Pending queue, not the record. The bulk **Re-sync titles** button (Users tab) and admin bulk `title-resync` route refresh everyone's stored `jobTitle` on demand — titles only, zero role writes, ever (§ design's own "existing people are never re-assigned" promise holds structurally, not just by convention). **Title Mapping's Matched column and its editor preview are live** against real data instead of a permanent dash. Design §12's pending-user holding screen ships fully built and wired to real `/access/me` data but stays **dormant** behind one flag (`AM_HOLDING_SCREEN_ENFORCING = false`) until Phase 6's cutover — real enforcement is still SharePoint-driven today, so a screen gating on the new tables would either never show or would incorrectly block real, working staff. **The single biggest thing to know before relying on any of this:** only **1 of 86** enabled staff accounts currently has a job title recorded in Entra at all (confirmed live) — so auto-assignment will correctly, silently do nothing for almost every new sign-in until job titles get entered in Microsoft 365, and that's a data gap, not a bug. Separately, the bulk **Re-sync titles** button is confirmed broken in production today — every batch Graph lookup fails (isolated to the `GET /users?$filter=id in (...)` batched lookup specifically — not Graph's actual `$batch` API, which this code doesn't use — root cause still under investigation) — while the single-person lookup the auto-assignment feature actually depends on is confirmed working live and is unaffected. Also closes three server-side gaps deferred from Phase 4 (a `deny` on Access Management or a dedicated-gate tool is now refused for any target, not just the caller; a no-op re-grant of an already-held permission no longer overwrites its own provenance or claims a false escalation). Help Center guide updated the same phase. **Correction, same day, in Phase 5's own fix-wave (commits `92da552`..`2c39da3`, all before Phase 6 began):** the bulk `Re-sync titles` button's every-lookup failure was root-caused to a GUID-casing mismatch in the batch Graph lookup and fixed; the button works now, its failure summary names the actual underlying error whenever a lookup genuinely fails, and the "1 of 86" figure above was also corrected — the real count once titles could actually be read was 26 of 28 synced users, and the Title Mapping tab's Matched count is computed live from whatever that count is today rather than citing either fixed number.

  **Phase 6** (2026-08-31, unmerged `feature/access-management` branch — not yet in a release) is the cutover itself: `/access/me` now returns each caller's real resolved tool set (role grants plus per-person overrides plus the two dedicated-gate tools, status-gated so a deactivated account always resolves to nothing), and a live parity comparison verified this new answer against the retiring SharePoint-based resolver for all 29 real `hub_users` before anything switched over — an Entra App Role export (roles are assigned to security groups, not people directly) filled in the 27 users the branch's own stored claims hadn't captured yet, and every difference it found was either explained (Mike's own two accounts, the payroll-gate union) or explicitly acknowledged by name (one client's own prior manual adjustment in the Hub) before Mike authorized the flip. With that authorization, `main/shared/accessTools.js` (a single cached snapshot plus one shared in-flight request) became the live source for both `buildUserInfo()`'s `allowedTools` and the sidebar filter, and the default inverted to fail-closed: no `hub_users` row, or a check that genuinely couldn't complete, now means zero tools, never the old "unconfigured matrix means show everything." A pending-user holding screen (Design §12) went live for anyone active with no role and no grant reaching zero tools — a deactivated account never sees it, since its "your account is being set up" copy would be a false claim about someone who used to have access; it polls for new access every 5 minutes plus a manual "Check for access now." A background check roughly every 10 minutes (about once a minute after a failure, keeping the last known answer meanwhile) picks up a role change or revocation without a fresh sign-in, and a tool that gets revoked while someone has it open returns them to Home quietly, no dialog, so the moment isn't announced to whoever's watching the screen. Payroll Review and Payroll Processing are unaffected — their visibility still comes from the live Entra `hub.payroll`/`hub.payrollmanager` roles, unioned on top of whatever this system separately grants. `main/shared/roleMatrix.js`'s SharePoint-reading half (`getAllowedToolKeys()`) is deleted outright; the two SharePoint lists are read only by the now-retiring parity-comparison tool, never for a live decision, and the plan is to rename both `RETIRED — ` in SharePoint once the branch ships. Two things still read the live Entra token directly rather than these tables — the Hub's general admin badge (`isAdmin`, used by several tools' own admin-only controls) and this screen's own `hub.admin` break-glass fallback — both deliberately left for **Phase 7**, which also adds the `withAuth` permission-mode work and folds break-glass into it; Title Mapping seeding (no active patterns exist yet, so every new sign-in lands on Pending regardless of title) is an operational to-do owed before this branch is handed over, not a Phase 7 code task. Help Center guide updated the same phase.

  **Phase 7** (2026-09-01, the last phase — unmerged, deployed to the live Function App under standing deploy authorization) folds every remaining server-side gate onto the same SQL tables, closes out the two Phase-6 leftovers, and adds an automatic offboarding sweep Mike requested mid-plan. `functions/src/lib/auth.js`'s `withAuth()` gains two new opts modes — `{ permission }` and `{ hubRole }` — both resolved through one per-request-memoized accessor (`getActorAccess()` in the new `functions/src/lib/accessActor.js`, which also absorbs `resolveCallerHubAccess()`/`loadTools()`/`loadRolePermissions()`/the dedicated-gate map, moved out of the route file `accessAdmin.js` that used to own them, since route files can't require each other). Break-glass now lives inside this one gate layer instead of one hardcoded 403 check: SQL is always resolved first — a caller whose real access already covers the check is never recorded as having used the emergency `hub.admin` Entra role — and only a genuine SQL-refusal-plus-Entra-`hub.admin` pass writes an audited `break_glass_used` row. `/access/me` itself stops auditing on every poll (it used to write a row every few minutes for any break-glass-only admin just from the sidebar's own repeated checks — a probe, not a use); every *enforcing* gate still audits on every genuine break-glass pass. All 8 remaining external server routes (`config.js` PUT, `feedback.js` ×3 plus its `isOfficial` badge affordance, `installs.js`, `touchAging.js`'s admin settings, `userIncreaseCycle.js`'s finance/admin routes, `accessManagement.js`'s `accessToolsSync`) move off `{ role: 'hub.admin' }`/hand-rolled Entra checks onto `{ hubRole: [...] }`, one deliberate holdout (`accessMigration.js`'s one-time import route stays on the Entra claim — bootstrap/recovery tooling gating itself on the same tables it might need to fix would be circular). Client-side, `buildUserInfo()` (`main/ipc/auth.js`) derives `isAdmin` from the same SQL `roleKeys` the launch's `/access/me` call already returns, instead of the raw Entra `roles` claim; 13 renderer admin-check sites and the two hardcoded 5-role tool arrays (Duo Management, Block Hour Report) in `app.js` collapse onto that single `isAdmin`/`_hasToolAccess()` source; three main-process gates (`userAudit.js`'s dashboard/billing checks, `clientTouchAging.js`'s `isAdmin()`, Timesheet Review's shared-job scan-machine check) move off the old Entra-claim reader onto the same access snapshot, and the two that used to fail *open* on an unreadable snapshot ("show everything, consistent with the sidebar" — a rationale that died the moment the sidebar itself went fail-closed in Phase 6) now fail closed instead; `main/shared/roleMatrix.js` is deleted whole, having lost every consumer. **New this phase, not in the original spec:** an hourly Functions Timer (`functions/src/functions/accessTimers.js`, `accessOffboardSweep`) reads every active `hub_users` row with a real Microsoft 365 object id, batch-checks each account's `accountEnabled` state via Graph (a sibling of the existing job-title reader, same managed identity, no new consent grant needed), and deactivates anyone whose account is confirmed disabled or genuinely gone from the tenant (a 404 on a direct re-check — never inferred from mere absence in a batch response) — never the reverse; a manually-flippable-on account is never auto-reactivated, on the same "never overwrite a human's own decision" principle Title Mapping already follows. Every deactivation is audited as a `System — M365 offboarding sweep` actor row. A same-named manual HTTP trigger (`POST access/admin/offboard-sweep`, gated `{ permission: 'access-management' }`) exists for troubleshooting but has no in-app caller — it's Azure-Portal- or API-invoked only. Deployed under the controller's standing deploy authorization (function count 104: 100 HTTP + 4 Timer); its first live hourly run genuinely deactivated two former employees' rows, confirmed correct with Mike in the same session. Two items explicitly punted rather than fixed this phase, both documented for whoever finishes the branch: three staff (Brian French, Chris Heck, Jacee Dobbs) hold roles only via Entra security groups and were never created as `hub_users` rows by the original import, which only carried direct assignments — a ready seeding script exists; and whether the two payroll tools' dedicated Entra gate should itself fold onto this same SQL system is now an open, Mike-requested follow-up (see Futures/Later below), not something this phase changed. Help Center guide, README, and this entry updated the same phase.
